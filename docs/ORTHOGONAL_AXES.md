## 1. 本文档的作用

本文档只做一件事：把 V4.6 的每一条验收条件**强制归属到一条轴**上，使「策略表现变化」与「工程可靠性变化」不能再互相冒充。
过去两轴混在一起，导致两种误判同时发生：改了几个动量参数被当作「工程进步」，加了一道 Fail-Closed 守卫被当作「策略退步」。
本文档给出轴的判定标准、21 条现有验收条件的逐条轴标注，以及一个必须诚实面对的结论：**当前 21 条里没有任何一条真正验收交易逻辑**。

## 2. 目标设计

### 2.1 两条轴的定义

| 轴 | 全称 | 管什么 | 本次目标 | 可替换性 |
|---|---|---|---|---|
| **STRATEGY_AXIS** | 交易策略轴 | 交易逻辑、选品（universe/ranking）、择时（regime→仓位映射）、配权（权重算法、上限） | **保持 / 演进**，不是本次重点 | 策略应当可整体替换而不动引擎 |
| **ENGINEERING_AXIS** | 工程实现轴 | 账户事实、状态机、数据身份与血缘、可观测性（运行快照）、Fail-Closed 守卫 | **升级**，本次重点 | 工程底座不可替换，是所有策略的共同前提 |

### 2.2 轴的判定标准（唯一裁决规则）

对任意一条能力 / 验收条件，问这三个问题，按顺序取第一个命中的答案：

| # | 判定问题 | 命中则标注 |
|---|---|---|
| Q1 | 改变它，会不会在**数据完全正常**的路径上改变「买什么、买多少、何时买」？ | 是 → 含 STRATEGY_AXIS 成分 |
| Q2 | 改变它，会不会改变**异常路径**的行为（数据缺失 / 状态非法 / 权限不足 / 历史被覆盖）？ | 是 → 含 ENGINEERING_AXIS 成分 |
| Q3 | Q1 与 Q2 同时为「是」 | → `BOTH` |

推论（本文档反复使用）：

- 「有没有守卫」是工程轴；「守卫触发后降到多少仓位」是策略轴。
- 「状态机有几个状态、迁移是否合法」是工程轴；「某个状态对应什么仓位区间」是策略轴。
- 一条验收条件如果只断言「某个类存在 / 某个枚举有 N 个值」，它一定不是策略轴。

### 2.3 正交性的硬性要求

| 要求 | 含义 |
|---|---|
| **每条验收条件必须且只能标注一次轴** | 允许取值 `STRATEGY_AXIS` / `ENGINEERING_AXIS` / `BOTH`；不允许留空 |
| **工程轴改动不得改变正常路径的决策结果** | 加固前后，同一份正常数据必须产出**逐字节相同**的目标权重；差异只允许出现在异常路径 |
| **策略轴改动不得放宽任何守卫** | 策略替换不得触碰 `quant/ledgers/guards.py`、`quant/fund_orders/states.py`、数据身份等工程模块 |
| **两轴不得共用同一个配置项** | 一个参数如果同时控制守卫强度与仓位大小，必须拆成两个参数 |

### 2.4 轴混淆的代码级反例（现存）

`quant/sentinel/levels.py:38-45` 在工程枚举 `SentinelLevel` 上直接挂了两个策略判断：

```
:38-40  allows_new_entries  → return self <= SentinelLevel.YELLOW   # "ORANGE 以上暂停开仓"
:42-45  is_risk_off         → return self >= SentinelLevel.ORANGE   # "ORANGE 以上只减不加"
```

「四级等级 + 非对称迟滞」是工程轴，但「ORANGE 以上就暂停开仓」是**策略参数**，被硬编码进了工程模块。
这意味着策略侧想把阈值调成 RED 才停开仓，就必须改工程代码——正交性在这里已经破了。这是 §4 中 GAP-A3 的根因。

### 3.3 必须点名的第一结论：策略轴验收覆盖率为 0

脚本自述把第 1–6 条称为「交易策略轴（成熟保留）」，其原文定义是：

> `app/v46_acceptance.py:6` — `- 交易策略轴（成熟保留）：环境安全、可移植、入口齐全（第 1-6 条）。`

「环境安全、可移植、入口齐全」三项没有一项属于交易逻辑。逐条核对 `c01`–`c06` 的函数体（`:32-80`）后可以确认：
**21 条验收条件中，没有任何一条断言过动量窗口、排名规则、权重上限、regime 阈值、换手容忍带或选品结果。**

也就是说，当前「6 条策略轴 + 15 条工程轴」的表述是**标签错误**——真实构成是「21 条工程轴 + 0 条策略轴」。
这正是用户担心的失真形态：策略轴看上去「已验收 6 条」，实际上策略逻辑处于**零验收**状态，任何人改动 `quant/features.py:58-68` 的评分公式都不会有任何一条验收条件报警。

### 3.4 与「两个平行世界」的交叉影响

`docs/ARCHITECTURE_INFLUENCE_MATRIX.md` §8 已记录：`quant/domain/`、`quant/ledgers/`、`quant/fund_orders/`、`quant/sentinel/`、`quant/decision/`、`quant/data_identity/` 无生产调用方。
这对轴标注产生一个直接后果：

| 观察 | 证据 | 影响 |
|---|---|---|
| 第 7–21 条（工程轴）验收的对象**几乎全部是孤立世界的模块** | `app/v46_acceptance.py:84,95,111,117,133,158,173,180,193,207,221,240,262,277` 的 import 全部指向 `quant/{ledgers,domain,fund_orders,sentinel,observability,data_identity,research_models}` | 工程轴「15 条全绿」描述的是**测试世界**，不是生产世界 |
| 生产实际链路无任何验收条件覆盖 | 生产入口 `quant/fund_pipeline.py`、`quant/strategies/tactical_etf/engine.py` 在 21 条中出现次数为 **0** | 生产链路同时处于「策略轴零验收 + 工程轴零验收」 |

结论：**在生产调用链打通前，21 条的通过率不能被表述为「V4.6 已达标」**，只能表述为「V4.6 的隔离模块在测试世界内达标」。

## 5. 验收方式

### 5.1 轴机制自身的验收条件

| 编号 | 验收条件（给定…当…则…） |
|---|---|
| AC-AXES-01 | **给定** `app/v46_acceptance.py` 的 `CONDITIONS` 列表，**当** 任意一条的轴字段不属于 `{STRATEGY_AXIS, ENGINEERING_AXIS, BOTH}` 三值之一，**则** 模块导入即抛异常，验收脚本无法运行 |
| AC-AXES-02 | **给定** 全部 21+ 条验收条件，**当** 统计 `STRATEGY_AXIS` 与 `BOTH` 的条数之和，**则** 必须 ≥ 5；若为 0 则整体验收判定为 FAIL（防止再次出现「策略轴零覆盖却显示全绿」） |
| AC-AXES-03 | **给定** 一份被冻结的正常输入数据与其对应的 golden 目标权重文件，**当** 仅做工程轴改动（新增守卫、新增日志、新增快照字段）后重跑，**则** 产出的目标权重必须与 golden 逐字节一致；出现任何差异即判定该改动「越界侵入策略轴」，FAIL |
| AC-AXES-04 | **给定** 一次策略轴改动（替换排名公式或调整动量窗口），**当** 对 `quant/ledgers/`、`quant/fund_orders/`、`quant/data_identity/`、`quant/sentinel/` 四个目录做 diff，**则** 变更行数必须为 0；非 0 即判定「策略改动混入工程轴」，FAIL |
| AC-AXES-05 | **给定** 验收脚本输出，**当** 读取报告尾部，**则** 必须能分别读到「策略轴 x/y 通过」与「工程轴 m/n 通过」两行独立统计，而不只是总计 |
| AC-AXES-06 | **给定** 任一配置文件，**当** 同一个键同时被工程守卫代码与策略计算代码读取，**则** 配置校验阶段报错并拒绝启动 |
