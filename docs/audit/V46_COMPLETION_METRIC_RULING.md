## 2. 两个数字到底在量什么

| | **验收门覆盖率** | **需求追溯落地率** |
|---|---|---|
| 数值 | 54/57 = **95%** | 17/63 ≈ **27%** |
| 来源 | `app/v46_acceptance.py` | `docs/V46_REQUIREMENTS_TRACEABILITY.md` |
| 分母 | 42 条**自定义验收条件** | 63 条**外部需求** |
| 通过判据 | 条件函数不抛异常 | 生产调用链**真实执行** |
| 回答的问题 | 「我立的规矩，我守住了几条？」 | 「说好要有的能力，真能用的有几个？」 |

**关键不对称：分母不是同一个东西。**
38 条验收条件是**自己给自己出的题**——题目范围由实现决定；
63 条需求是**外部给定的题**——不会因为没实现就消失。

用验收门比率对外，等于用「自测通过率」冒充「需求完成率」。

## 3. 为什么验收门比率经不起对外使用：三条硬证据

### 证据一：验收门在验证生产不可达的模块

`docs/audit/V46_PRODUCTION_WIRING_AUDIT.md` 逐模块追溯（W2-1~W2-4 落地后复核）：

- c22 / c23 / c24（下单权限闸门 Fail-Closed）验证的 `permission_gate`，
  现已经 `run_daily._record_decision_plans` → `order_factory` 接入生产；
  但 `execution_service`（真实提交）**仍零生产调用方**——验收门验证的是「闸门逻辑正确」，不是「真实单能下出去」。
- 领域闭环相关条件验证的 `TargetPortfolio` / `DecisionProposal` / `OrderIntent`，
  现已由 `run_daily` 真实构造并写入前两本账（W2-2 / W2-3 / W2-4）；
  但写入的是**计划账**，下游「计划 → 真实持仓」的链路仍被有意断开（PAPER 零真实单）。
- 模型目标账、决策计划账经 W2-2 / W2-3 已通电记账；但**记账 ≠ 落地**——
  验收门条件只断言「记账动作正确」，不断言「该决策驱动了真实下单」。

这些变化让「验收门验证的是生产不可达模块」这一旧论断失效；但核心问题仍在：
**验收门条件验证的是「模块/契约正确」，而追溯矩阵验证的是「生产调用链真实走到」**——
两者分母不同、口径不同，前者永不能作为对外完成度。

### 证据二：分母会随实现移动（已实测）

新增一条验收条件，分母 +1、分子 +1，比率**上升**；
删掉一条做不到的条件，分母 −1，比率**也上升**。
一个能被自己调整的指标，不具备对外承诺的资格。

**实测（本轮两次亲历）**：
> - 新增 c33 一条，比率从 84% **升**至 85%——而系统能力只增加了 63 条需求中的 1 条；
> - 随后登记 #41 / #42 两条已知缺口，比率又从 85% **跌**至 81%——而系统能力**没有任何减少**，只是把原本隐形的窟窿写进了分母。
>
> 同一天里，这个数字先涨后跌，与真实进展无关。它衡量的是「我承认了多少缺口」，不是「我完成了多少」。

对照：63 条需求是审计阶段（A1–A4）从 26 节补充需求中固定下来的，**不随实现变动**。

### 证据三：追溯矩阵口径已被独立复核

本次生产接线审计用完全独立的方法（从 `app/*.py` 入口反向追调用链）重做了一遍，
结论与追溯矩阵的 `TESTED` 判定**相互印证**。这个量级是可信的，不是悲观估计。

## 4. 生效的表述规范

### ✅ 正确表述

> V4.6 需求落地率 **19%**（63 条需求中 12 条已在生产调用链真实执行并有测试覆盖）。
> 工程内部验收门 36/42 通过，该指标衡量既有实现的自检完整性，**不代表需求完成度**。

### ❌ 禁止表述

| 错误写法 | 问题 |
|---|---|
| 「V4.6 完成度 86%」 | 用自测率冒充完成率 |
| 「验收覆盖率 86%，接近完成」 | 「接近完成」无依据 |
| 「核心功能已全部落地」 | 订单链、前两本账均未通电 |
| 「完成度 86%（另有 19% 口径）」 | 并列即误导；追溯矩阵口径是唯一对外口径 |
| 「Fail-Closed 权限闸门已上线」 | 闸门存在但生产不可达，应写「已实现，待 W2-4 接入生产」 |

### 状态词标准（追溯矩阵用词，全项目统一）

| 状态 | 含义 | 可否计入落地率分子 |
|---|---|---|
| `TESTED` | 有测试 **且** 生产调用链执行 | ✅ 是 |
| `IMPLEMENTED_UNTESTED` | 代码存在，无测试 | ❌ 否 |
| `PARTIAL` | 部分实现，或实现了但生产不可达 | ❌ 否 |
| `NOT_FOUND` | 未实现 | ❌ 否 |
| `DEFERRED` | 明确延后（如 Riskfolio 依赖 Wave 3） | ❌ 否，但单独列示 |

**铁律**：**代码存在 ≠ 已实现；测试通过 ≠ 已落地。** 只有生产调用链真实执行才计入。

## 5. 验收门比率的正当用途（保留，但限定场景）

不废弃这个指标，它有真实价值——只是价值不在「对外报完成度」：

1. **回归防护**：34 条中任何一条转红 = 既有能力被破坏，立即可见。
2. **不变量锁定**：如 c32 锁定评分公式序数，改公式必然触发失败。
3. **重构安全网**：Wave 2 大改生产链路时，验收门是判断「有没有改坏」的基线。

**限定**：仅在工程内部文档、CI 输出、变更评审中使用，且必须标注「内部工程卫生指标」。

## 8. 2026-08-02 复核附录（c37-c49 + Wave 3 落地后）

本次落地新增 13 条验收条件、8 条待办条件，两个口径的最新取值：

| 口径 | 2026-08-01 | 2026-08-02 | 变化 |
|---|---|---|---|
| 验收门机械覆盖率（内部） | 36/42 = 86% | **54/57 = 95%** | 分子 +18、分母 +15（c50–c54 升入 CONDITIONS，c55/c56/c57 仍挂起） |
| 追溯矩阵 `TESTED`（对外） | 12/63 ≈ 19% | **17/63 ≈ 27%** | **+5 条 PARTIAL→TESTED**（c50–c54 接线：REQ-DATA-03/04/STATE-03/RUN-03/BT-01） |

### 8.1 为什么做了这么多，对外数字一点没动

新增的 6 个治理模块（`data_health`、`confirmation_budget`、`state_synthesis`、
`clock_consistency`、`run_archive.credibility`、`backtest_unknown_price`）与
Riskfolio 适配层，全部处于「**有实现、有测试、生产零调用方**」状态。

按追溯矩阵 §0.2 的判定规则——「生产零调用方一律不得标 `TESTED`」——它们只能标
`PARTIAL`。这条规则正是上一版「21/21 全绿却带病发布」的补丁，本次不得为了让数字
好看而例外。

变动只体现在**缺口形状**：`NOT_FOUND` 20 → 16，`PARTIAL` 26 → 30。
一句话概括：**能力在长，落地未动。**

### 8.2 曾出现 100% 及其处置

c37-c49 上移到 `CONDITIONS` 后，`PENDING_CONDITIONS` 一度为空，验收门显示
**49/49 = 100%**。回归测试 `test_pending_conditions_are_not_silently_dropped`
立即红灯——这正是该护栏的设计意图。

处置方式**不是**削弱护栏，而是承认「空清单 ≠ 没有缺口」，把 8 条真实存在的接线
缺口登记为 c50-c57，比率回落到 86%。同时在 `run_all()` 中加入「覆盖率达 100% 时
强制打出反向提示」的逻辑，防止未来再次出现「全绿即完工」的误读。

### 8.3 顺带修复的一个生产 Bug

`quant/strategies/tactical_etf/trend.py` 原实现**先截断、后归一**：归一会把已被
`max_single_weight` 截断的权重重新放大回上限之上，集中度约束长期形同虚设。
该函数经 `run_daily:136 → engine:174` 生产可达，属真实风险敞口。
已改用 `cap_single_weights`（归一后仍受限），并由验收 c44 锁定「归一后逐项 <= 上限」。

> **裁定原则仍然不变**：验收门比率任何时候都不得单独对外引用；
> 对外完成度唯一口径是追溯矩阵 `TESTED`，当前 **17/63 ≈ 27%**（2026-08-02 v1.5「全打接线」后）。

### 8.4 2026-08-02 v1.5「全打接线」为何让对外数字动了

此前 c37-c49 落地后对外数字「一点没动」（§8.1），根本原因是新模块「生产零调用方」，
按 §0.2 判定规则只能标 `PARTIAL`。v1.5 的指令是「全打接线，不再造新能力」——只把
公认、生产入口已存在的调用点接上，不写新模块。于是 5 条需求的「生产调用链真实执行」
从无到有，落地率由 12/63≈19% 升至 17/63≈27%。

**诚实性修正**（同见追溯矩阵 v1.5 变更记录）：c55 此前登记「现网回测建立在收盘价即时成交
假设、收益被系统性高估」系误判——经核实 `run_event_backtest` / `run_fund_event_backtest`
本就实现 T+1 执行；本轮接线实为补「信号日绝不成交」的**硬后置条件**（违约即 BLOCKED），
而非切换执行模型。c55（确认预算接入试探路径）如实挂起：生产无试探路径
（`regime_ensemble` 零生产调用方，`run_daily` 无当前持仓输入），强行接假闸门只会制造
「已接线」错觉，故不伪造。
